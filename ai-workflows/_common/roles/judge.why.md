# Why Judge?

![Judge role visual](img/judge.png)

When there are rules, sooner or later you need a judge.

That is mostly why the role has such a short name. We did not need something elaborate like `Governance Compliance Supervisor`. There are rules, and this participant checks the rules, so: **Judge**.

Ordinary agents live inside those rules. They should not be able to rewrite the boundaries whenever a boundary becomes inconvenient. Judge sits outside normal team collaboration and periodically checks whether the agents are still following what was agreed.

It does not need to watch every conversation continuously. Usually it can wake up on a schedule, inspect the relevant communication/activity, look for violations or abuse of authority, and report what it finds to the Human.

There is another important reason for the separation: **the Human should still understand the rules.**

Imagine repeatedly telling Judge:

> Add whatever rules you think we need for this.

That sounds convenient. After enough repetitions, though, the Human may technically own the governance system while no longer being able to explain what its rules actually are or why they exist.

So the Human writes the rule.

Judge can say that the rule conflicts with another rule. It can point out a security problem. It can fix typos, clean up Markdown, keep terminology consistent, and apply the same rule to the places where it needs to appear. If clearer wording would change the meaning, Judge can propose it — but the Human must accept that wording before it becomes the rule.

The intended path is:

`Human writes rule -> Judge validates it -> Judge applies it consistently -> Human reads the resulting change`

This gives Judge considerable power over the **integrity** of the rule system without giving it ownership of the Human's policy decisions.

And because rules only matter when somebody checks them, Judge periodically comes back and asks the simple question its name implies:

> Are we actually following the rules?
